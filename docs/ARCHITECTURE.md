## Phase 7 mistake evidence and corrective practice

Migration `0007_red_shockwave.sql` adds `weakness_definitions`, version-scoped `activity_weaknesses`, immutable `mistake_occurrences` and immutable `mistake_practice_attempts`. The English editorial catalog has five concepts: past simple/present perfect, narrative sequencing, everyday collocations, polite requests and evidence-based inference. Eight graded activities have explicit mappings. Study/reflection blocks and ordinary tags never classify errors. Definition IDs survive publication changes; removing an identity fails safely in the seed and requires an explicit migration. The seed is transactional and repeatable and does not write personal evidence.

A successfully persisted incorrect Phase 4 attempt creates one occurrence per authored activity/version/weakness mapping in the same transaction. Source attempts retain answers, actual scores and feedback; occurrences reference them without duplicating these fields. A trigger validates the source owner, incorrect result, mapping and original timestamp. Unique source/weakness keys prevent transport duplicates. Intentional retries produce distinct immutable attempts. Malformed, unauthorized, locked, stale or unsaved submissions create no evidence. Matching retains its real partial score and is classified only at collocation activity level, without diagnosing individual pairs.

`npm run db:mistake-backfill` is a separate transactional `INSERT ... SELECT` with conflict protection. It classifies existing incorrect assessed attempts using matching historical content versions and preserves their timestamps. Repeating it creates no duplicates. This is derived historical evidence, not fabricated assessment history. It never reads FSRS ratings and never changes source attempts. Version-scoped mappings remain available for historical backfill even when retired from current practice. No lesson grading or order changed, so lesson content version **2 remains unchanged**.

Recurrence is the total of lesson error occurrences plus failed corrective attempts for that weakness. The UI also displays the source counts separately. Two or more errors means repeated difficulty; recurrence never resets. `needs practice` means one error without a strictly later successful corrective attempt; `repeated` means the same active state with at least two errors; `recovered` means a successful corrective attempt is strictly later than the most recent error from either source. Equal timestamps do not establish recovery. A later error reactivates the area. Ordinary correct lesson answers do not establish corrective recovery. A repeated mistake is evidence of repeated difficulty, not a diagnosis of learner ability. Recovered does not mean permanently mastered.

Recent mistakes means the newest **20 error records**, ordered by actual error timestamp descending and immutable ID descending, with no rolling time-window claim. Counts aggregate all evidence in PostgreSQL; they are not mutable counters. All personal queries are scoped by server session identity and the selected language. History includes retired definitions. Current prompt/choice labels are shown only when the content version still matches; older responses retain their saved identifiers and grading feedback rather than borrowing revised wording.

The authenticated `/mistakes` Center provides skill/status/repeated filters, recent error context and aggregate states. `/mistakes/[weaknessId]` shows history and recurrence. `/mistakes/[weaknessId]/practice` requires that the current learner has recorded evidence for that weakness. Selection is deterministic: current published mapping and definition, active course language, then curriculum level/unit/lesson/activity order and stable activity ID. Existing catalog presence is the course publication convention; Phase 7 does not add a separate lesson publication system. Unavailable, retired, unknown, wrong-language or stale targets fail safely.

Corrective practice uses the existing public exercise allowlist, answer controls, normalization and server evaluator. Hidden expected answers and explanations remain server-only until grading. The strict request accepts weakness/activity/version, submission UUID and validated answer; user, correctness, recurrence and status are never accepted. A user row lock serializes concurrent submission replays, content locks protect grading, and each intentional retry appends a separate result. Update-denying triggers protect both history tables; user deletion cascades for fixture/privacy cleanup. Application paths do not delete historical evidence.

Mistake practice writes only its own attempts: it does not advance or complete lessons, unlock course content, create Phase 4 attempts, alter Phase 5 vocabulary evidence or update FSRS cards/history. `/review` links to Mistake Center with the real count of active weaknesses; it does not mix corrective exercises into FSRS sessions. Phase 7 itself adds no Daily orchestration. Phase 8 coordinates these existing systems as described below; placement, proficiency analytics, XP and adaptive learning remain later work.

## Data model

Implemented: users (UUID, case-insensitive unique email), GitHub accounts, persistent sessions, verification records, languages (code, display/native names, writing direction, active flag), learner_profiles (per-user native/learning language, optional internal estimate, target level/exam, time budget/timezone), courses, course_levels, units, lessons, lesson_activities, lesson_prerequisites and lesson_progress. The course points to a learning language; the learner profile supplies the native→learning direction. Content identity/order/version and learner progress are distinct.
Constraints: language FKs, cascading profile/progress removal, supported study budgets, positive ordering/version/duration, unique order within a parent, unique lesson/owner progress, valid progress state and completion timestamp. No real user is seeded and there is no unauthenticated data API.

Phase 4 adds `exercise_attempts`: a server-generated UUID, authenticated user, lesson/activity/content version, transport submission UUID, validated submitted answer, correctness, score (0–1), timestamp and a feedback/model-answer/explanation snapshot. A database trigger prohibits updates. User deletion may cascade for fixture cleanup or an explicit future privacy operation; ordinary app code never updates or deletes attempts. Phase 5 adds vocabulary tracking. Phase 6 adds review scheduling; a mistake center remains Phase 7.

## Phase 5 vocabulary model

`vocabulary_senses` stores stable IDs independent of headword spelling, language, lemma/display form, part of speech, editorial CEFR level, definition and optional notes. Separate example, tag, collocation, family and activity-association tables provide relational lookup. Family edges are ID-based and cannot point to themselves. The validated editorial source contains 16 representative English senses connected to existing B1/B2 lessons. `activity_vocabulary` distinguishes `introduces`, `practises` and `context`; context alone never changes learner state. Matching targets name an authored left-side ID, so evidence reflects the individual pair's correctness instead of assigning the overall partial score to every word.

`user_vocabulary` separates `introduced_at`, `last_seen_at` and `saved_at`. On successful traversal of an introductory study block, the same transaction that advances lesson progress records the introduction once. The server-graded attempt transaction writes one `vocabulary_evidence` row per explicitly targeted sense, keyed by attempt and sense. Transport replays return the existing attempt without new evidence; deliberate retries create new immutable attempts and evidence. Owner identity is derived from the session; no client-supplied user or correctness value is accepted. User deletion cascades personal rows. Repeating the seed changes only editorial rows, never user state, attempts or evidence.

The UI derives a cautious practice status from persisted introduction and attempt counts: `not encountered` (neither), `encountered` (introduction only), `practising` (one correct or any incorrect), `familiar` (at least two correct, none incorrect) and `strong` (at least four correct, none incorrect). An incorrect event lowers the label to `practising`; no status claims durable mastery. Saving without an encounter does not change status. Phase 5 added metadata and presentation to existing blocks without changing their order or grading, so lesson content version 2 is preserved. Review scheduling is a separate Phase 6 model.

Migration `0005` is additive and was applied to Neon development only after isolated PostgreSQL 17 migration/seed/E2E passed. Read-only whole-row hashes of all Phase 0–4 tables, including auth/session/profile/progress/attempt data, matched before and after migration and both seed passes. Phase 5 passed owner manual validation and was merged without interpreting practice as review history.

## Phase 6 review model

`ts-fsrs` **5.4.2** is pinned exactly in the lockfile. One application-owned configuration, `ts-fsrs-5.4.2-v1`, uses requested retention `0.90`, maximum interval `36500` days, learning steps `1m`/`10m`, relearning step `10m`, short-term scheduling enabled and fuzz disabled. The four UI ratings map directly to library `Rating.Again`, `Hard`, `Good`, and `Easy`. No owner-specific weight optimization is performed. The domain accepts an authoritative server `now`, and all due comparisons use absolute `timestamptz` values. The profile timezone is for display only. FSRS state is neither the Phase 5 practice label nor CEFR proficiency, and review scheduling does not certify learning.

Migration `0006_sour_salo.sql` adds `review_cards`, `review_sessions`, `review_session_items` and `review_history`. A card belongs to an authenticated user and stable vocabulary sense, with explicit `recognition` kind, the complete ts-fsrs Card fields, indexed due timestamp, revision and scheduler version. A partial unique index limits each user to one active session, and each session selects at most 20 due cards in deterministic due/ID order. The headword is the front; definition and example are fetched only when the current answer is revealed. The session, item status and reviewed count persist through refresh. The user explicitly finishes after all items are reviewed or safely skipped as stale.

Lesson introduction and trusted targeted practice each ensure a New card inside their existing transaction. A bookmark alone does not. The separate, repeatable `db:review-backfill` command creates New cards for earlier eligible Phase 5 rows; their due time is the bootstrap time, and it writes no historical ratings. Editorial `db:seed` never changes review state. Existing lesson/content version 2 remains unchanged. Phase 6 creates no mistake inbox, daily planner, XP/streak or adaptive parameter optimizer.

`POST /api/review/rate` checks the Better Auth owner, exact origin and a strict input schema; the browser supplies only session/item/card IDs, a submission UUID and one explicit rating. A transaction locks the owner session, item and card, checks the current pending item and due/revision, runs ts-fsrs server-side, increments card revision, appends one history row and marks the item reviewed. Unique submission/item constraints and the lock serialize concurrent retries; identical transport replays return the original result. A database trigger rejects history updates. User deletion still cascades personal rows for the established fixture/privacy strategy. Review statistics come from persisted history, not browser state.

Migration `0006` first passed disposable PGlite/PostgreSQL checks, then was explicitly authorized for Neon development. Read-only repeatable-read snapshots of every existing Phase 0–5 public table matched before/after migration and both backfill checks. The first backfill created fresh eligible cards in `New` state, all due immediately; the second created none. No review history was invented, and no older table changed. The local regression test proves saved-only vocabulary is excluded; Neon development had no saved-only rows at this gate. `db:inspect` and `db:verify` passed after migration. Production infrastructure remains untouched.

Progress rows contain user_id, lesson ID and content version. Authorization derives user identity server-side, never from a submitted user ID. Progress increments only at the expected position and version, so replayed/stale steps cannot skip a block; completion is idempotent. A graded block requires at least one saved attempt before traversal, but an incorrect answer may still continue. Correctness and completion remain separate. A changed lesson content version starts afresh when the learner next opens it. There is no XP or inferred mastery.

## Exercise boundary and evaluation

`activity-schema.ts` defines strict, concrete payloads. Multiple choice has stable option IDs and exactly one correct ID; reorder uses token IDs (including repeated display words); matching defines a complete ID bijection. Four text types use explicit curated accepted forms and normalization metadata. Definitions reject missing/duplicate/unknown answer IDs. `en/exercises.ts` supplies eight exercises across the existing five lessons, proving all seven types. The initial translation is curated Romanian→English; it is not an arbitrary translation evaluator.

Trusted payloads remain on the server. `presentExercise` constructs an explicit public allowlist for the current exercise only: prompt, instructions, metadata, options/tokens/matching collections or source/context text. It omits correct IDs, accepted forms, option feedback, explanation and normalization metadata before submission. No editorial catalog or evaluator is imported into the client bundle. A prior submitted answer and its own feedback may be loaded after refresh. Completed review is available only after traversal.

`POST /api/exercises/attempt` checks the owner session and same-origin request, rejects oversized/malformed/extra fields, derives the profile's language, then calls the repository. The transaction locks the lesson version and user progress, checks active-course membership, prerequisites and the current activity, validates the answer type/IDs, grades trusted persisted content and inserts an immutable attempt. The client never supplies correctness, score or user ID. A unique user/submission key and serialized progress lock deduplicate transport replays; reusing a key with changed content is rejected. An intentional retry generates a new key. No answers are inferred from an old content version.

Text evaluation normalizes Unicode to NFC, trims surrounding whitespace and collapses repeated whitespace. Case sensitivity and tolerance of final ASCII `.`, `!` or `?` are explicit metadata. Accents, apostrophes and internal punctuation are preserved. Submitted text is stored as entered; normalization is only for evaluation. Multiple choice, reorder and text score 0 or 1; matching also returns the fraction of correctly paired items, with overall correctness requiring every pair. Translation accepts only authored alternatives. There is no AI grading or semantic-equivalence claim.

All five lessons and the course move intentionally from version 1 to 2 because graded practice changes completion semantics. Seed leaves owner profiles/progress and attempt history unchanged; opening a revised lesson resets its existing progress through the Phase 3 version rule. Existing activity IDs remain stable, reflection moves after practice, and transactional order shifting permits new blocks without unique-order conflicts. Removing a published activity ID fails the seed and requires an explicit reviewed migration.

The checked-in course source is validated for language tags, CEFR ordering, consecutive per-parent order, unique IDs, activity payloads and levels, and backward-only prerequisite references (preventing cycles). The seed upserts catalog rows without touching authentication, profile or progress. Server queries derive locked/available/in-progress/completed from current-version progress and prerequisite completion. The lesson page and every mutation require the Phase 2 owner session; a direct action cannot start or finish locked content. Japanese can later add validated orthography/readings payloads without repurposing English-only columns.

## Phase 8 Daily Learning model

Migration `0008_striped_amphibian.sql` adds only `daily_sessions` and `daily_session_items`, their foreign keys/indexes/checks and four guard triggers. Existing lessons remain content version 2. No seed or backfill creates Daily history. User deletion cascades sessions and items; editorial lesson/weakness references remain protected by foreign keys.

Session identity is uniquely `(user_id, language_code, study_date)`. `study_date` is a PostgreSQL date derived on the server with `Intl.DateTimeFormat(..., {timeZone}).formatToParts`; UTC slicing and browser dates are not authoritative. The session snapshots the profile’s allowed daily duration, IANA timezone, language, local date, `daily-v1` planner version, estimated planned minutes and creation time. The current profile timezone determines which local date is Today. Changing it can move the current date and select/create a different day’s plan; it never rewrites an earlier snapshot. Day rollover creates nothing until explicit Start. Previous plans remain historical and language changes never reinterpret their sources.

Ordered relational items store kind, label/focus snapshots, estimated minutes, a finite target, source references, a creation-time event-count baseline and monotonic derived progress. Lesson references include content version, start position and target position; mistake references identify the weakness. Status is pending, completed or unavailable with consistent timestamps. Unique indexes enforce one Review block, one lesson segment, distinct mistake areas and distinct item positions per plan. Checks bound goals, minutes, counts and kind-specific references. Immutable guards prevent target/snapshot edits, decreasing progress and reopening resolved tasks/plans. Deferred constraint triggers require one to five items whose estimates exactly sum to the session’s bounded planned minutes.

### Deterministic workload and balance

`src/server/daily/planner.ts` centralizes all estimates. Each accepted Review rating costs **0.5 minutes**, capped at **20 ratings**. Each distinct corrective area costs **2 minutes**, capped at **3 areas**. Each lesson activity costs `clamp(ceil((lesson.estimatedMinutes / activityCount) * 2) / 2, 0.5, 3)` minutes: rounded up to a half minute, at least 0.5 and at most 3. All six profile durations use the same policy, and summed estimates never exceed the goal. These are workload estimates, not a study timer.

Selection first reserves one current lesson activity and one corrective area where available and affordable. It allocates due Review up to 40% of the goal within those reserves, then corrective areas up to 20% (at least one where affordable, at most three). Remaining budget buys as many consecutive activities as fit in the single current reachable lesson. Spare budget after that segment goes to additional due reviews, then additional corrective areas, within the caps. No category is filled with invented work, no future lesson is traversed and a small catalog can yield less planned work than the selected goal. Display order is Review, ranked corrective areas, lesson segment.

Review availability comes from Phase 6’s owned, published due cards. An active same-language Review session is reused through its existing route; Daily never creates one. Another language’s active Review session excludes Review from a new plan because Phase 6 permits only one active session per learner. Mistake candidates come from Phase 7’s published, reachable, non-recovered areas, ranked by repeated first, recurrence descending, last error descending, stable ID ascending. Course selection uses the existing recommended in-progress/available lesson and prerequisite rules. Grammar and other skill labels come from selected activities; vocabulary is added only for explicit `introduces`/`practises` associations. Context mentions alone do not create vocabulary work. Daily has no standalone vocabulary or grammar grading engine.

### Start, source evidence and resolution

The protected `/daily` page and Overview render either a preview or the persisted Today plan. The explicit `POST /api/daily/start` is used instead of a Server Action to provide a small strict empty-body boundary, directly testable for forged fields and same-origin checks. It derives owner identity from the real session and language/budget/timezone from the database, rejects all client plan fields, and recomputes trusted candidates at Start. A learner row lock serializes concurrent Starts, a profile shared lock protects the snapshot, and the unique day identity backs up idempotency. No-work Start creates no empty session. GET/prefetch never creates Daily history.

Reconciliation locks the owned, language-scoped Daily session and updates only its own progress. Review completion counts accepted immutable `review_history` rows for that learner and language at/after Start, up to the current server time, minus the baseline of matching evidence already present at Start. Baselines exclude tied or future-dated pre-existing records. Again, Hard, Good and Easy all count as performed reviews. Transport replay creates no new source row, so it creates no new Daily credit. The finite target can finish before the Phase 6 session finishes; more Review remains available independently. No scheduling state is copied or edited and FSRS ratings never become mistakes.

A mistake task completes after one accepted saved Phase 7 corrective attempt for its target weakness after Start, with the same baseline/replay rules. Both correct and incorrect attempts count as performed practice; recovery is not required. A lesson segment completes when owned progress for the planned content version reaches its stored target position. Partial progress is position minus the planned start, clamped to the finite target. Activities stay contiguous and use existing server grading, introductions, prerequisite checks and traversal; Daily does not start, advance or complete lessons itself.

Daily completion means planned work was performed. It does **not** mean the learner mastered the material. If a pending lesson version becomes stale, its route becomes unreachable, a weakness loses valid published practice, or no published review cards remain, that item becomes explicitly unavailable without source writes, replanning or performed-work credit. Already-performed trusted evidence is recognized first. The plan’s `completed_at` records resolution when every task is completed or unavailable; unavailable counts remain separate and the UI says “available plan” when any task was skipped. Restored content, extra activity or newly due work never reopens the resolved snapshot. No browser completion/target/minutes API exists, and browser storage does not persist Daily state.

There is no Daily historical backfill, production/Neon mutation during local work, CEFR inference, placement test, full analytics, XP, streaks or adaptive optimization. Phase 8 remains in progress until separately authorized Neon validation, push/draft PR/CI and real-owner manual validation pass. Phase 9 is not authorized.

## Design

Working name: Lingua Studio. Ink-blue learning surface, crisp cool-neutral cards, serif editorial emphasis only inside the journey and course cards. Blue is the action accent. Both palettes share semantic tokens. The Overview now reads a real due-review count; there are no fabricated streaks, XP, mastery values or certification claims. ## Quality and security

Validate at server boundaries; never log connection URLs. Keep credentials in ignored environment files; .env.example contains placeholders only. Migrations run explicitly, never during builds or page visits. Auth, ownership checks, CSRF/session protections and rate limits must precede personal-data endpoints. Persist timezone-aware event timestamps; compute streak dates using the learner timezone in the relevant phase.

The application pages require a server-validated owner session. The public sign-in page gives a setup state when OAuth is incomplete; there is no mock login. The profile server action derives the user ID from that session, validates input with Zod and writes only that user's row. Migrations `0001`–`0003` are applied on the Neon development database. The owner mismatch and logout boundaries passed live browser checks in Phase 2; an integration test covers expired signed sessions. Phase 3's authenticated E2E uses an ephemeral linked owner fixture under a process-only test owner ID, not an application bypass, and deletes its rows afterward. Auth library errors are logged generically to avoid exposing OAuth state or PKCE parameters. The example JSON lesson is a schema fixture, not an available course. Do not claim CEFR certification or official Cambridge endorsement. Verify Cambridge sources in Phase 16.
